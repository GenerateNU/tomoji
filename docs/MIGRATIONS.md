# Database migrations

Migrations are defined in dated files under [convex/migrations/](../convex/migrations/)
and registered in [runner.ts](../convex/migrations/runner.ts). The shared component
setup lives in [convex/lib/migrations.ts](../convex/lib/migrations.ts), with
transformations in [convex/models/migrations.ts](../convex/models/migrations.ts).
The runner processes records in batches and tracks progress; deploying the code
alone does not run a migration.

## Before running

Use your personal development deployment configured in `.env.local`
(`CONVEX_DEPLOYMENT=dev:...`), without a deployment-key override. The current schema
requires `firstName` and `lastName` and does not accept legacy `users.name`.
User sync and the name backfill use the account email for a missing or blank
first name and `""` for a missing last name. Creator `username` remains optional.

Existing incompatible records must be converted under a compatible deployment
before the strict schema can deploy. The retained backfills do not bypass schema
validation. For empty or already compatible databases, install dependencies and
deploy normally with `just bd` or `bunx convex dev --once`.

These backfills cover users and creators. Any populated legacy workflow tables
need a separate conversion plan. Preserve a snapshot before migrating data you
need to keep.

Username lookups use the normalized value in the `by_username` index. Before
enabling these checks on a populated deployment, ensure existing nonblank
usernames are trimmed and lowercase and resolve duplicate values. The backfill
does not normalize existing choices. It only renames existing values that exactly
match `creator_<userId>` for that creator, treating them as legacy generated names.

### Moving from the old migration paths

Finish or cancel any running `migrations:backfillUserNames` and
`migrations:backfillCreatorUsernames` jobs before deploying the dated files.
Check those names with the component's `lib:getStatus` query. To cancel an old
job, use its exact name, for example:

```bash
bunx convex run --deployment dev --component migrations lib:cancel \
  '{"name":"migrations:backfillCreatorUsernames"}'
```

Progress is keyed by the full exported function path. The dated paths have fresh
progress, so their first run rescans records even if the old functions completed.
Old status entries remain historical; they do not show completion of the new
paths. Both transformations are safe to rerun and preserve already migrated data.

## Run migrations

After deploying the code, run the registered migrations in order:

```bash
bunx convex run --deployment dev migrations/runner:runAll
```

`runAll` runs the user-name backfill first, then the creator-username backfill.
It skips completed migrations and resumes interrupted ones.

Available migrations:

- [2026_09_26_backfill_user_names.ts](../convex/migrations/2026_09_26_backfill_user_names.ts)
  exports `backfillUserNames`. It preserves existing name parts, fills missing parts from
  cached WorkOS data, and retains a whole legacy name as `firstName` only when no
  split name parts are available. If the selected first name is missing, empty,
  or whitespace-only, it uses the account email. It removes legacy `name` and
  uses `""` for a missing last name.
- [2026_09_26_backfill_creator_usernames.ts](../convex/migrations/2026_09_26_backfill_creator_usernames.ts)
  exports `backfillCreatorUsernames`. It fills missing usernames and replaces exact
  `creator_<userId>` values with `creator_` plus a random 12-character lowercase
  alphanumeric suffix. It preserves all other values, including empty strings and
  names generated by a previous run of this version. Each candidate uses the same
  normalization and indexed uniqueness check as profile updates, in the same
  mutation as the write. It retries collisions up to five total attempts, then
  returns `conflict` with reason `username_generation_failed`. The index is not
  itself a unique constraint. This does not change signup behavior or make
  username required.

Both preserve document IDs and relationships. To select one migration, use `run`
with its full function path:

```bash
bunx convex run --deployment dev migrations/runner:run \
  '{"fn":"migrations/2026_09_26_backfill_user_names:backfillUserNames"}'
```

Add `"reset": true` to deliberately rescan from the beginning, including records
added after an earlier completed run:

```bash
bunx convex run --deployment dev migrations/runner:run \
  '{"fn":"migrations/2026_09_26_backfill_creator_usernames:backfillCreatorUsernames","reset":true}'
```

Passing `{"reset":true}` to `runAll` resets the entire registered sequence.

Add `"dryRun": true` to preview one batch without saving changes. The intentional
`DRY RUN` result rolls the batch back. Preview each migration separately, since a
dry run does not execute the full sequence. For example, preview the first batch
of the username backfill even if it has already completed:

```bash
bunx convex run --deployment dev migrations/runner:run \
  '{"fn":"migrations/2026_09_26_backfill_creator_usernames:backfillCreatorUsernames","dryRun":true,"reset":true}'
```

## Check completion and resume

The runner can return before scheduled batches finish. Check status:

```bash
bunx convex run --deployment dev --component migrations lib:getStatus \
  '{"names":["migrations/2026_09_26_backfill_user_names:backfillUserNames","migrations/2026_09_26_backfill_creator_usernames:backfillCreatorUsernames"]}'
```

Wait until both entries report `isDone: true` and `state: "success"`. If a batch
fails, fix the reported cause and rerun the same command without `reset` to resume
from saved progress.

Verify that IDs, record counts, and creator-to-user links are preserved. Migrated
users should have a nonblank `firstName`, a string `lastName` (possibly `""`), and
no legacy `name`. Scanned creator profiles should have a username and no exact
`creator_<userId>` value remaining. New profiles can still be created without a
username afterward.

## Add a migration

1. Add a `YYYY_MM_DD_migration_title.ts` file in `convex/migrations/`. Use
   underscores because Convex module paths do not allow hyphens. Import the
   shared `migrations` instance from `../lib/migrations` and export a
   `migrations.define(...)` definition. Keep transformation logic in `models/`.
2. Register its generated `internal` function reference in the `runAll` list in
   `runner.ts`, after any migrations it depends on. The list defines execution
   order; filenames alone do not register or order migrations.
3. Test the transformation and runner, document any schema compatibility steps,
   deploy the code, and run `runAll`. Deploying alone does not start it.

Keep registered filenames and export names stable once deployed, since renaming
them creates a new progress entry and causes a rescan.
