# S3 media foundation

This is the shared S3 layer for issue #58. It does not expose an upload route or attach media to a user or submission yet. Those are separate changes.

## Buckets and deployment configuration

Use a separate private bucket for each environment (development/QA and production). Set these variables on the **matching Convex deployment**, not in browser-facing `NEXT_PUBLIC_*` variables:

| Convex deployment                  | S3 media bucket                 | Region      |
| ---------------------------------- | ------------------------------- | ----------- |
| Dev (`hallowed-retriever-646`)     | `tomoji-dev-media-478867930449` | `us-east-1` |
| Production (`descriptive-jay-817`) | `tomoji-media-478867930449`     | `us-east-1` |

| Variable                                      | Purpose                                                                             |
| --------------------------------------------- | ----------------------------------------------------------------------------------- |
| `S3_MEDIA_BUCKET`                             | Exact bucket name for that deployment                                               |
| `S3_MEDIA_REGION`                             | Bucket's AWS region                                                                 |
| `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` | Credentials for a least-privilege IAM principal, when no workload role is available |

The AWS SDK uses its standard credential provider chain. Do not put AWS credentials in `.env.template`, the browser, or Git. Configure both S3 settings on each Convex deployment before deploying this stack; `readMediaConfig` also fails closed if either is absent.

Each contributor's personal dev deployment is separate. Existing teammates must run the
two `bunx convex env set` commands in [Contributing](../CONTRIBUTING.md#step-4--give-convex-the-workos-values)
before their next `just bd`; merging this PR does not propagate env vars to their deployments.
The production deployment is configured with the production bucket and region. Any new
preview or staging deployment needs its own bucket/region mapping before deploying.
`just convex-env` configures WorkOS only. CI's local typecheck/tests do not require S3
deployment variables, but a Convex push does because the config declares them required.

For each bucket, keep Block Public Access enabled, ACLs disabled, and default encryption enabled. The IAM principal signing uploads needs `s3:PutObject` on `staging/*` and `media/*`, and `s3:GetObject` on `staging/*` (plus `media/*` when backend serving is added). The copy from staging to media requires source read and destination write permissions. Scope the resource ARNs to that environment's bucket; do not grant cross-environment access.

Configure bucket CORS for `POST` from the exact frontend origin(s) in that environment. Do not use `*` for origins. Browser `GET` access is not needed for profile pictures: the intended profile-picture reader is the Tomoji backend.

## Shared upload behavior

`convex/lib/s3.ts` issues a 15-minute presigned POST for a random `staging/<kind>/<uuid>` key, where `<kind>` is `profile-picture` or `video-submission`. The policy requires the selected content type and an object size between 1 byte and the cap: 2 MiB for profile pictures or 250 MiB for video submissions. The browser uploads directly to S3; no large file body passes through Convex or Vercel.

After upload, `inspectMediaObject` checks the key prefix and S3's reported size, content type, and ETag. This is a metadata check, **not** proof that the bytes decode as an image or playable video. `promoteMediaObject` copies the inspected object to a server-owned `media/<kind>/<uuid>` key, conditional on the inspected ETag. This prevents the still-valid upload grant from changing an accepted asset. The caller must bind staging and permanent keys to an authenticated pending upload before calling these helpers; a client-provided key alone is not authorization.

Set an S3 lifecycle rule to remove abandoned `staging/` objects after a short retention period (for example, one day). Do not apply that rule to `media/`. The later upload-route PR must specify the cleanup and retry behavior for failed promotions.
