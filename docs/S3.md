# S3 media uploads

This is the direct-to-S3 backend for issue #58. The browser sends file bytes to S3, not through Convex or Vercel. Convex keeps ownership, validation, and private read access under typed functions.

## Buckets and deployment configuration

Use a separate private bucket for each environment (development/QA and production). Set these variables on the **matching Convex deployment**, not in browser-facing `NEXT_PUBLIC_*` variables:

| Convex deployment                      | S3 media bucket                     | Region            |
| -------------------------------------- | ----------------------------------- | ----------------- |
| Personal dev (`<your-dev-deployment>`) | `tomoji-dev-media-<aws-account-id>` | `<bucket-region>` |
| Production (`<production-deployment>`) | `tomoji-media-<aws-account-id>`     | `<bucket-region>` |

| Variable                                      | Purpose                                                                             |
| --------------------------------------------- | ----------------------------------------------------------------------------------- |
| `S3_MEDIA_BUCKET`                             | Exact bucket name for that deployment                                               |
| `S3_MEDIA_REGION`                             | Bucket's AWS region                                                                 |
| `AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` | Credentials for a least-privilege IAM principal, when no workload role is available |

These are naming examples, not values to paste. Ask a TL for the actual bucket name
and region for your environment. The AWS SDK uses its standard credential provider
chain. Do not put AWS credentials in `.env.template`, the browser, or Git. Configure
both S3 settings on each Convex deployment before deploying this stack;
`readMediaConfig` also fails closed if either is absent.

Each contributor's personal dev deployment is separate. Existing teammates must run the
`just convex-env` command in [Contributing](../CONTRIBUTING.md#step-4--give-convex-the-workos-and-s3-settings)
before their next `just bd`; merging this PR does not propagate env vars to their deployments.
Fill in `S3_MEDIA_BUCKET` and `S3_MEDIA_REGION` in your untracked `.env.local` first.
For production, preview, or staging, configure the matching bucket/region on that
deployment separately; the contributor command targets personal dev.
`just convex-env` copies WorkOS and S3 settings, not AWS signing credentials. CI's local typecheck/tests do not require S3
deployment variables, but a Convex push does because the config declares them required.

For each bucket, keep Block Public Access enabled, ACLs disabled, and default encryption enabled. The IAM principal signing uploads needs `s3:PutObject` and `s3:GetObject` on both `staging/*` and `media/*`. The copy from staging to media requires source read and destination write permissions, and private media delivery requires read access to the permanent objects. Scope the resource ARNs to that environment's bucket; do not grant cross-environment access.

Before browser uploads can work, configure bucket CORS for `POST` from the exact frontend origin(s) in that environment. Do not use `*` for origins. Browser `GET` access is not needed for profile pictures: Convex reads and returns those bytes to authenticated clients. Configure a least-privilege AWS credential source for the action runtime; bucket and region variables alone cannot sign an S3 request. These AWS credentials and CORS rules are not configured yet, so this code is not a claim that live uploads work.

## Shared upload behavior

`media.requestUpload({ kind, contentType, assignmentId? })` checks the caller before issuing a 15-minute presigned POST for a random `staging/<kind>/<uuid>` key. A profile-picture request accepts any active, synced user and no assignment ID. A video-submission request requires an active assignment owned by the calling creator. The policy requires the selected content type and an object size between 1 byte and the cap: 2 MiB for profile pictures or 250 MiB for video submissions. It returns `{ uploadId, url, fields, expiresAt }`.

The browser POSTs `fields` and the file to `url`, then calls `media.completeUpload({ uploadId })`. That action checks the caller against the stored grant, HEADs S3 to ensure the object exists and its size, content type, and ETag match policy, then copies it to a unique server-owned `media/<kind>/<uuid>` key conditional on the inspected ETag. A database mutation commits one winning copy. Repeating completion returns the same media ID; a losing concurrent copy is removed best-effort. The browser cannot submit an arbitrary S3 key or URL as proof of an upload. This is a metadata check, **not** proof that image/video bytes decode successfully.

For profile pictures, completion also sets `users.profilePictureMediaId`. Creator and company-member profile responses expose that ID, not a legacy profile-picture URL. WorkOS synchronization does not copy avatar URLs into users. The frontend calls `media.getProfilePicture({ mediaId })` to retrieve the current picture bytes from Convex and build a local Blob URL; S3 never grants browser GET access to profile pictures. For videos, the completed media ID remains bound to the creator's assignment. `media.getVideoUrl({ mediaId })` gives the creator, that assignment's company, or an operator a five-minute signed GET URL. A later submission route must accept this owned media ID, not a client-supplied video URL; this change does not create submissions or modify their existing `draftUrl` field.

Before deploying to a database containing legacy `users.profilePicture` URLs, follow the [profile-picture cleanup rollout](MIGRATIONS.md#remove-legacy-user-profile-picture-urls). Company logo URLs in `companies.profilePicture` are separate from user pictures and remain unchanged.

Set an S3 lifecycle rule to remove abandoned `staging/` objects after a short retention period (for example, one day). Do not apply that rule to `media/`. A grant can be completed for up to 24 hours after its 15-minute upload window; after that it is rejected. If S3 copy succeeds but the database commit fails, the action attempts to remove its unique copy. Cleanup failures are logged without hiding the original error and need operational follow-up. Lifecycle rules are not configured yet.
